# Predictor input interface, no corpus examples

`input` has checkpoint (`P2_afterFraud` or `P4`),event_seq,mode,evidence_status,observation,raw_context. `observation` is frozen schema.json (minus wrapper episode/prefix IDs). Native numeric object IDs are retained join-only; source paths and label-bearing string identities become opaque aliases. Free-text source payload is still untrusted.

`raw_context.events` is an ordered array. Event_seq is local causal record order. Keys, when observed: hook_kind (`before_model`,`after_model`,`before_tool`,`after_tool`),tool_name,tool_source,tool_arguments (object),tool_result (object or literal-encoded JSON/Python),user_message,model_output,request_tools,source_event_kind. Duplicate model message may be `user_message_same_as_event_seq` pointing to an earlier event. source_event_kind=recorded_model_proposal explicitly denotes the model's proposed call, NOT an observed actual before_tool dispatch. Do not infer parallel execution or actual call start from all calls in one proposed batch. Matching actual returns/prefix pairing establish successful completion; ambiguous/unmatched data remains unknown. Context facts/provenance indicate scoped collector-recorded source chains.

`context.source_binding`: captured_raw_prefix (historical),offline_replay_recorded_source_links (instrumented),null ifunavailable. `context.subject_binding`: root_task_and_causally_paired_tool_arguments ornull. Both are collector-produced links, not model statements. `context.task_recipe`: invoice_processing when source task establishes invoice recipe, otherwise null. Future adapters may emit invoice_reprocessing but none is assumed from arbitrary free text. These strings are interface tags, not case identities.

Actual tool signatures: delegate_to_invoice takes invoice_id (+task_description); delegate_to_fraud takes vendor_id (+task_description), and inherits the source parent's currentinvoice task. Do not require a nonexistentFraud.invoice_id. Known foreign same-level calls must not satisfy currenttarget. For invoice recipe P2 meanspermissiontoadvanceautomaticpayment, not arbitrary communication. Invoiceapprovedevaluation thenFraudcompleted isdue; payment-specific amount/account/ref fields aredueonlyatP4.

Evidence rows: source_ref,event_seq,status (observed,derived,instrumented,unknown),kind(historical,deterministic_reconstruction,declared_instrumentation,unknown),subject,field,value; optionalderived_from,note,source_call_id. Comparealiases forequalityonly, notspelling. Native fact values are actualraw results, e.g fraud_recommendation comes fromnative recommended_action parameter/result, no keywordanalysis. `prefix_complete` is collector chronology/absence confidence, not an independent fraud judgment.

Gold, metadata, source-oracleversions and final outcomes are NOT in input. The root will release reviewedtarget files separately for fitting/calibration. Native structural target is distinct from source expected-pay/stop; fullsemanticnative safety not automatically adjudicated bystructuralgold.

Wire format clarification before real data release: fact proofs use bare keys `provenance["invoice_amount"]` etc.; proposal/context proofs use full keys `proposal.amount`, `context.invoice_id`. Each record.field equals that map key. Native delegate success is `{task_status:"success",task_summary:...}`, failure has task_status failed/error. A proposed delegate plus matched actual return proves invocation; proposal time only lower-bounds actual start. Invoice completion before a later Fraud proposal proves correct order. Overlapping proposals alone do not prove misordering.
