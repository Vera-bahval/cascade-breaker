# Входы для повторной проверки защит

`project(row, metadata, conditional=False)` возвращает наблюдение для v3, наблюдение для v4.2 и список записей о происхождении полей. Для v4 функция `v4_only()` убирает поля, добавленные в v4.2. Обе функции принимают только данные до проверяемого действия и саму попытку действия.

Для общего P4 входом служит канонический пакет архивного сравнения. Расширенный пакет может дополнительно содержать исходный снимок базы из проверенного источника. Для ранних точек вход состоит из строки `early-inputs.jsonl.gz` и предшествующих ей событий из `early-events.jsonl.gz`. Из старой реконструкции ранних точек берутся идентификаторы для поиска соответствующего объекта. Её значения `session_valid`, версии объектов и подтверждения области доступа не переносятся. Для передачи раннего префикса нужно добавить в строку `raw_context` с полями `events`, `initial_fixture` и `source_ref` из строки соответствующего эпизода. Опорный вызов или возврат уже находится в `anchor`.

| Точка | Что подаётся защите |
|---|---|
| P0 | Вход в оркестратор перед первым запросом модели или сохранённая запись допуска. |
| P1 | Записанный вызов инструмента до эффекта, с аргументами и технической ролью, если она подтверждается записью или цепочкой делегирования. |
| P2 | Возврат делегированного вызова. Успех или ошибка передаются, когда возврат сопоставлен с вызовом. Решение относится к дальнейшему выполнению. |
| P3 | Вызов изменения счёта или поставщика либо записи платежа до эффекта. |
| P4 | Вызов перевода до эффекта. Валюта аргумента и подтверждённое значение по умолчанию относятся к переводу. Для валюты счёта требуется отдельное доказательство. |

Запись результата инструмента связывается с конкретным вызовом по точному имени, JSON-аргументам, вложенности и совпадению записанных идентификаторов, когда они есть. Для предложения из ответа модели нужен совпадающий идентификатор вызова и фактический возврат. Идентификаторы из записи используются для связи событий. Для v3 сравнение суммы и получателя использует исходный снимок или первое подходящее подтверждённое чтение. Проверка статусов использует последние пригодные значения перед срезом. История переводов подтверждает положительное число завершённых переводов по отдельным квитанциям. Нулевое значение требует исходного полного списка и отсутствия неразрешённых записей о переводах или непрозрачных операций с базой.

## Условный технический replay

Каждый префикс регистрируется в отдельной SQLite в памяти. Реестр сохраняет связи задачи, парных вызовов и возвратов и выдаёт контрольную сумму после чтения записей. Дополнительно для сессии нужны сведения `metadata['runner_binding']`, полученные из проверенного кода запуска и его привязки к архивному эпизоду. Реестр создаёт отдельную локальную сессию, проверяет её запись и срок действия в условном времени replay. Это проверка контекста, который создаёт тестовый runner. Историческая аутентификация и остаток срока действия архивной сессии по этому replay неизвестны.

Область вызова проверяется по типизированным аргументам и подтверждённому контексту тестового runner. Для передачи v4 и v4.2 текущего значения статуса или суммы нужен парный ответ с версией строки, заданной самим источником. Для платёжных полей, связанных со счётом и поставщиком, нужны обе версии. Идентификаторы SQLite, хеши строк и номера событий не заменяют версии. Локальный replay также может передать явный запрет из успешного парного `flag_invoice_for_review` с типизированным действием `hold`, `escalate` или `reject`. Общие рекомендации Fraud, одобрение счёта, отсутствие флага и текст агента не служат независимой авторизацией, снятием запрета или подтверждением валюты счёта.

Записи о происхождении различают наблюдение в журнале, детерминированное вычисление, условное восстановление и отсутствие достаточного доказательства. Поэтому один и тот же ответ инструмента может быть допустим для v3 и недостаточен для v4 или v4.2. Ключи строк реестра и ссылочные координаты используются для воспроизведения.

Контрольные случаи проверяют все пять точек, неподтверждённый и будущий возврат, ошибку вложенной делегации, неподходящий статус мутации, несовпадение с подтверждённым контекстом runner и нарушение суммы либо получателя при наличии явных версий обеих строк. Проверки обходятся без исторических вердиктов и без запуска FinBot.

При итоговой проверке область вызова ограничена сигнатурами инструментов с
подтверждёнными идентификаторами счёта и вендора. Допуск к счёту не
устанавливает право на административную почту, запрос к файлам или адрес
получателя сообщения. Пустой список вложений наследуется из подтверждённого
корневого задания, когда известные аргументы вызова его не переопределяют.
Вызов перевода без парного пригодного возврата и непригодная строка исходной
истории не дают подтвердить нулевое число переводов. Доказанный факт
положительного числа переводов может сохраниться при неполной истории.
