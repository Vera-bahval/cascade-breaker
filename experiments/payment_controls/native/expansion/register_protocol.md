# Public payment register and native FinBot simulation

The unit is one opaque supplier group and one opaque target obligation from a frozen public paid-invoice frame. The public register establishes paid source records and supports frame selection. Native settlement, authorization, linkage and case labels are experimental fixtures. The local fixture retains public payment cents and relative source chronology where available. The supplier's identity and native reference are replaced. The native study uses mock transfers and local SQLite. No paid provider call is needed for native scoring.

## Selection and fixtures

Use the complete admitted source frame and require unique supplier and target obligation groups. Group cases by presence of a documented earlier distinct invoice, then sort within each group by the generalized source block and the SHA-256 of the fixed experiment seed and obligation reference. Allocate consecutive pairs to two settlement-status regimes in alternation. Within each pair assign one linked and one distinct prior transfer, with starting position selected by a fixed hash per group. Odd rows remain in their allocated groups. This keeps authentic pairs balanced even when an individual source block is small. The source byte hash, allocation file and code/specification hashes are frozen before scoring.

Each vendor uses the existing C or G trusted simulator profile with five historical paid invoice rows. The target obligation retains the exact source payment amount through a cents-to-Decimal-to-float round-trip. Its issue date follows a common translation of the source date and its due date is a study default. The sibling uses an earlier distinct same-supplier source payment amount and translated issue date when available. Source references, payment dates and the as-of comparison stay in the private allocation. A synthetic sibling fallback has the same amount and issue date as the target and is reported apart from the source-backed subset.

For linked exposure, an initial mock FinStripe create_transfer settles the target row. In the distinct comparison it settles the sibling. FinStripe list_transfers verifies the row binding by vendor and invoice foreign keys, successful status and creation before ledger read time. The primary, stale-approval regime leaves both rows approved. In the secondary regime, the row linked to the completed transfer is marked paid. The distinct target remains approved in both regimes. A distinct sibling source payment supplies a temporal comparison, with the sibling recorded paid before the target issue date and target payment subsequently recorded. The public register cannot prove that no other real transfer had occurred by the source cutoff.

## Boundaries and outcomes

Collect stock Fraud get_invoice_details, get_vendor_risk_profile and get_vendor_invoices tool returns before any proposed additional transfer. Stock Fraud history includes paid invoice rows. Its risk aggregates lack payment transaction links. Its current row may reveal paid status in the secondary regime. A separate added-evidence view exposes a scoped mock FinStripe ledger projection with its read cutoff and native receipt creation time. The stock Fraud agent has no FinStripe ledger tool. The added-evidence view asks whether the current invoice has a completed transfer in the complete local register. HOLD for the same obligation and CONTINUE for a distinct obligation applies to this exact duplicate check with the other prerequisites fixed by the fixture. Stock evidence under stale approval may be insufficient. CONTINUE provides no business authorization.

Record existing FinBot P1 and P4 V1 and V2 outputs against a native snapshot and tool args. P1 before Fraud is an observability check. P1 before Payments and P4 use an identical scripted marker for completion of neutral Fraud review so settlement link can be examined at the payment boundary. Run the stock probe in enforcement mode at P4 against the proposed FinStripe tool call and check the receipt and database or absence of writes. After a stop, separately exercise the ungated mock tool from its unchanged state to measure simulated principal that would move. For a distinct target, its first matching receipt is a valid simulator completion. Labels follow FinBot requirements of approval and at most one transfer per invoice. A duplicate-risk check before payments would block an already settled obligation regardless of status. The existing P1 V1 check is narrower and is scored against both its approval precondition and duplicate-risk coverage. P4 V1 should block an already linked repeat and allow a distinct target. V2 is a text baseline. Record all outcomes and count misses, interruptions in valid paths and duplicate principal by group. These controlled replays estimate behavior under the specified conditions. They do not estimate autonomous agent frequency, real payment authorization or population prevalence.

Six mechanical checks precede held-out scoring and stay outside its denominators. They cover fresh payment, linked approved, linked paid, distinct paid, changed proposal amount, and approval above the manual-review threshold. Positive cases reach the actual mock FinStripe MCP server and write linked rows. Freeze the blind packet and gold digests as a separate receipt before any optional model panel. Raw public inputs, allocation, outcomes and provider-packet material stay under the ignored runtime directory.

The added-ledger baseline is a strict equality lookup of current invoice and vendor IDs against completed transactions in a complete scoped mock ledger. Its early outcome tests only the duplicate condition. The simulation labels are constructed using that condition, so performance measures conformance to the stated invariant rather than discovery of new fraud.

For reproduction, invoke register.py from the repository root with the following phases. Use fresh ignored runtime directories. The controls phase uses its own directory and shows the six mechanical checks. The seal phase takes a source JSON list, rejects duplicate target/supplier groups and reversals of known chronology, and seals the private plan. The packets phase runs independent SQLite seeding to freeze clean packets and separate gold. The evaluate phase verifies the sealed code and plan, builds its own database, runs native checks and writes the unredacted outcomes locally and aggregate results next to this document. The per-case runtime outputs are needed to audit exact native linkage.
