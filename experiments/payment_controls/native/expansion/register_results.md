# Точное совпадение с уже проведённым платежом

На 45 записях из реестра District of Columbia воспроизвели два исхода в штатном симуляторе FinBot. В одной ветви предварительный платёж был связан с тем же счётом. В другой использовали действительно существующий отдельный счёт того же поставщика, по которому в публичном реестре платёж датирован раньше выставления целевого счёта. В FinBot перенесли суммы и относительную хронологию. Ветки и статус счёта в SQLite назначили по заранее зафиксированному правилу. Публичный реестр подтверждает учётную запись о перечислении и датировку. Он не даёт полного среза фактических платежей к любому историческому моменту. Проверка охватывает захваченную страницу источника. [DC Payments](https://vendorportal.dc.gov/DCPayments)

В основной группе 22 предварительные квитанции связаны с целевым счётом, 23 относятся к другому счёту. Перед вызовом Payments штатное V1 остановило 11 из 22 повторов. Во всех 11 сработал признак статуса paid. Ещё 11 уже проведённых платежей сохранили статус approved, и этот шаг пропустил каждый. Перед mock FinStripe V1 увидело связь с завершённой транзакцией и остановило все 22 повтора. Все 23 отдельных обязательства прошли штатный локальный вызов с созданием ровно одной привязанной записи. При отключённой проверке та же локальная операция создала вторую запись для каждого из 22 повторов на сумму 65 970,51 условного USD. С включённой проверкой эта сумма равна нулю. [Агрегаты](register_results.json)

Ещё 171 исходная запись задаёт контрольный набор с искусственным вторым счётом на ту же сумму. В нём поздняя проверка остановила 86 из 86 повторов и пропустила 85 из 85 отдельных обязательств. При чтении журналов FinStripe ключом служат идентификаторы поставщика и счёта, а не равенство сумм. В основном наборе равная сумма встретилась у одного из 23 отдельных обязательств. Это свойство контролируемых прогонов, поэтому доли описывают проверку на данном входе и не оценивают частоту ошибок самостоятельного агента. [Агрегаты](register_results.json)

Штатный Fraud получает текущий счёт, профиль и список счетов со статусом paid. Квитанции FinStripe в этой точке ему недоступны. После добавления чтения полного локального реестра строгая проверка связи дала ожидаемый ответ на всех 45 основных входах. Ожидаемые метки построены по тому же условию. Результат подтверждает, что в этот момент при наличии квитанции можно отдельно проверить повторную оплату, при этом весь Fraud-анализ этим условием не исчерпывается. [Протокол](register_protocol.md)

Шесть механических проверок выполнены отдельно. Контрольные суммы плана, кадров наблюдения, эталона и результатов зафиксированы. Повторное чтение SQLite нашло 432 завершённые тестовые записи в 216 изолированных пространствах имён. У 108 пространств обе записи относятся к одному счёту, у остальных 108 к разным. Все записи совпали со счётом по пространству, поставщику и сумме. Этот итог включает отдельный вызов с отключённой проверкой после каждой штатной остановки. [Механические проверки](register_mechanics.json) · [Фиксация](register_freeze.json) · [Эталон и входы](register_binding.json)

Эксперимент проверяет вторую попытку по тому же внутреннему ID счёта. Повторная регистрация одного обязательства под новым ID требует отдельной проверки идентичности обязательства. Успешный mock-перевод подтверждает поведение текущего кода в изолированной базе, а не право на фактическую оплату.

## Повтор на данных New Britain

Тот же протокол применили к 244 поставщикам из официальных ведомостей New Britain. Для каждого нашли две разные записи со счётом и перечислением у одного поставщика. Первая оплата датирована раньше выставления целевого счёта. При отборе исключили совпадения нормализованных названий с захваченной страницей округа Колумбия. Этот фильтр уменьшает риск пересечения, хотя не связывает филиалы и варианты юридических имён. [Ведомости New Britain](https://www.newbritainct.gov/gov/common-council/agenda-minutes-live-stream-n-videohtm)

Перед Payments штатное V1 останавливало платежи по статусу paid и пропустило все 72 случая со статусом approved после успешного перевода. Перед FinStripe проверка блокировала повторы в обоих режимах. При включённой поздней проверке сумма повторных переводов равна нулю. Поздняя проверка пропустила все 34 действительно разных счёта с совпадающей суммой. Показатели относятся к mock FinStripe с назначенными условиями, включая одну заранее подготовленную транзакцию и один предложенный перевод.
