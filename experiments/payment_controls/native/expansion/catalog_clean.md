# Как FinBot обработал штатные счета в архиве

Для 40 дополнительных счетов сохранились первичные записи GPT-4o-mini. В пяти прогонах OFF FinBot дважды записал флаг HOLD для исходного счёта. После одного из этих флагов FinStripe всё равно завершил перевод. В 80 прогонах с контролями в режиме наблюдения это произошло в 27 прогонах по 22 счетам. Во всех этих записях авторский сценарий ожидал PAY. Наблюдение показывает расхождение решений внутри workflow и частоту его появления в данном архиве. Договорная обоснованность HOLD отдельно не размечалась.

В каждой графе число прогонов и число разных исходных счетов. В shadow у каждого счёта два повтора. В OFF у пяти счётов по одному.

| Событие | GPT-4o-mini OFF | GPT-4o-mini shadow |
| --- | ---: | ---: |
| Всего | 5 / 5 | 80 / 40 |
| Payments успешно прочитал тот же счёт | 5 / 5 | 77 / 40 |
| FinStripe вызван для того же счёта | 4 / 4 | 75 / 40 |
| Успешная запись HOLD того же счёта | 2 / 2 | 31 / 25 |
| Явное `flagged=false` | 0 / 0 | 0 / 0 |
| HOLD перед первым чтением в Payments | 2 / 2 | 29 / 24 |
| HOLD перед первым вызовом FinStripe | 1 / 1 | 27 / 22 |
| После HOLD перевод не завершился | 1 / 1 | 4 / 4 |
| Завершился перевод | 4 / 4 | 75 / 40 |
| Дубликат, неправильная сумма или расхождение журнала с БД | 0 / 0 | 0 / 0 |
| FinMail подтвердил отправку поставщику, письмо указывает тот же счёт | 5 / 5 | 80 / 40 |
| После перевода письмо содержало формулировку об оплате | 4 / 4 | 75 / 40 |
| После HOLD без перевода письмо содержало формулировку об удержании или проверке | 1 / 1 | 4 / 4 |

**Что подтверждает журнал.** Для HOLD требовали успешный ответ `flag_invoice_for_review`, совпадение ID в запросе и ответе, `flagged=true` и рекомендацию hold либо escalate. Во всех найденных записях рекомендация была hold. Первое чтение Payments и вызов FinStripe сверялись по ID исходного счёта. Идентификаторы завершённых переводов сверялись с финальной БД, сумма каждого перевода — с исходной суммой. Подтверждение отправки FinMail связано с ID поставщика в доставке и с ID или номером счёта в письме. Формулировки об оплате и проверке считаются по фиксированным выражениям в подтверждённых письмах. Сверка устанавливает основное сообщение о статусе. Адресация и обязательства дополнительных внутренних уведомлений в этой постановке не заданы.

**Технические исходы и пропуски.** Все 85 записей имеют финальный снимок и не имеют ошибки уровня раннера. В shadow три записи содержат завершившийся ошибкой этап Fraud. В двух из них Payments всё же выполнил перевод. В одной, `clean_30/r1`, исполнение до Payments не дошло, а FinMail сообщил о незавершённой проверке. Это технический исход без записи HOLD. У 35 из 40 счетов отсутствует OFF-повтор.

**Повторы.** В двух повторах shadow факт HOLD меняется у 19 из 40 счетов, факт завершения перевода — у 5 из 40. В пяти доступных парах OFF и shadow с одинаковым исходным счётом и номером повтора 0 решения по HOLD расходятся в трёх случаях, завершение перевода — в одном. Модель и хэш ролей совпадают. Разные ревизии раннера и отсутствие рандомизации ограничивают это сравнение наблюдаемым расхождением.

## Покрытие других исполнителей

Для DeepSeek и Luna проверены по 297 записей в матрицах и по 297 записей заданий основного прогона. В дополнительных попытках проверены 16 записей DeepSeek и 20 Luna. Во всех этих источниках совпадений с 40 исходными счетами по ID или по нормализованным сумме и тексту **0**. Контрольные суммы 14 архивов сверены с манифестом. Среди 19 исторических архивов FinBot477 проверены 2 325 записей сценариев в доступных манифестах, совпадений **0**. Два архива из этих 19 не содержали манифеста сценариев. Они не расширяют проверенное покрытие. Парной оценки DeepSeek и Luna для этих 40 счетов на основе проверенных материалов нет.

## Воспроизведение

Архив OFF взят из исходной ветки `research/first-prototype` по коммиту `2476ceb9d88d003ce86e106c7d1644151ec283c1`. Локальный архив shadow проверен по ранее записанному SHA-256 в `experiments/local_guards/data/archive/provenance.json` общего рабочего каталога. В `catalog_clean.json` записаны SHA-256, найденные ID, порядковые номера событий и сводки. Чтение конечных состояний служит только сверке эффектов после прогона. Входы для моделей в этом разборе не собирались.

Из корня `cascade-breaker-publication`, после bare clone исходного Git-репозитория:

```sh
python3 experiments/payment_controls/native/expansion/catalog_clean.py /path/to/bare-repo |
  diff -u experiments/payment_controls/native/expansion/catalog_clean.json -
```
