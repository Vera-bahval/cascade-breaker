# Проверка ограничения по текущему счёту

В ранней точке P1 проверяется действие `delegate_to_payments` после отчёта Fraud. В P4 проверяется перевод или запись оплаты. Экспериментальный `V1_SCOPED_RESTRICTION` включается через список проверок `GuardRuntime` у этих границ. По умолчанию действует прежняя регистрация. Метод использует штатные `GuardContext`, `GuardResult` и `check`. Снимок всей БД и контекст workflow по-прежнему поставляет вызывающий код.

Исходный V1 считает флагом любой вызов `flag_invoice_for_review` без ошибки на уровне выполнения инструмента. Обычный ответ инструмента при семантической ошибке может содержать `flagged=false` и `output.error` при пустой ошибке исполнения. Другая причина ложной остановки возможна, если вызов относится к другому счёту. Текущий инструмент Fraud связывает запись с `invoice_id`, добавляет заметку в счёт, ставит `flagged=true` в ответе и возвращает `flag_reason` и `recommended_action`. Рекомендации `hold` и `escalate` сохраняют статус счёта. `reject` переводит `submitted` или `processing` в `rejected`, а в других статусах оставляет запись рекомендации. Контракт Fraud проверен по [исполнению записи](../../../../finbot/finbot/tools/data/fraud.py) и [ответу агента](../../../../finbot/finbot/agents/specialized/fraud.py).

Применимые ограничения V1 по статусам, сумме, пройденному Fraud, реквизитам и прошлым переводам сохраняются. Для дополнительного запрета нужны совпадающие идентификаторы в запросе и успешном ответе Fraud и соответствующая заметка в текущем счёте. Подтверждённый флаг по другому счёту или подтверждённый отказ записи без отметки в текущем счёте оставляет в силе обычные условия V1. Единственная отметка прежней сессии без своего ответного события, несколько отметок и расхождение между ответом и счётом ведут к `REVIEW`, если обычные условия ещё не дали `BLOCK`. Исполнение останавливается в обоих случаях. Завершение Fraud или дальнейший статус `approved` сами по себе не снимают ограничение. В обследованном наборе нативных действий снятие флага отсутствует.

## Проверка до разметки

На двух исходных архивах TH601 в новой SQLite активный HOLD повторно записан штатным инструментом, затем поданы исходные аргументы из архивов на реальные границы guard runtime. У обеих проверок по две остановки для HOLD и по два разрешения для чистой ветви. Это восемь проверок на двух связанных архивных префиксах. Фактический перевод в этой проверке не вызывался. [Проверенные результаты](guard_controls.json)

Отдельные регрессионные изменения фиксируют семантическую ошибку, флаг по другому счёту, один сохранённый HOLD без события текущего workflow, несогласованный ответ, несколько отметок и сохранение проверки суммы. Прогон дал 73 ожидаемых вердикта и подтвердил остановку на `REVIEW` в режиме `enforce`. Эти изменения не включались в архивную выборку.

В общей выборке выполнены 238 парных проверок с координатами записи для каждого операнда. Для каждого blind ID исходный и новый guard получили один и тот же контекст; до вызова проверены SHA-256 пакета и исходного журнала. События поданы до предложения действия. Итоги выполнения здесь не использовались. Для ранних 34 HOLD заметка реконструируется из успешного ответа архива и проверенного механизма добавления записи. В остальных ранних случаях заметку даёт снимок инструмента (85) или реконструкция записи статуса (1). В поздней точке заметка берётся из связанного чтения счёта во всех 118 случаях. Источник поздней истории переводов ограничен видимыми до отсечки квитанциями. Влияние одного невидимого завершённого перевода показано отдельным полем возможных решений.

| Отсечка | Пар | Обе дали BLOCK | Обе дали ALLOW по наблюдаемым данным | Различий |
| --- | ---: | ---: | ---: | ---: |
| До поручения Payments | 120 | 34 | 86 | 0 |
| До FinStripe | 118 | 32 | 86 | 0 |

32 поздних запрета остаются запретами при неизвестной истории. Поздние 86 разрешений условны. Эти числа описывают решения, а допустимость действия оценивается отдельно. Успешные флаги в этой выборке относились к текущему счёту и во всех случаях рекомендовали HOLD. Поэтому архивное сравнение не измеряет частоту устраняемых ложных остановок при флаге по другому счёту или семантическом отказе записи. Использовано ноль платных вызовов.

Версии, исходные данные и хеш результата сохранены в [манифесте](guard_freeze.sha256). Построчный результат для соединения с независимой разметкой находится в `.runtime/validation-population/guard_paired.json`. Повтор из корня checkout:

```sh

```
