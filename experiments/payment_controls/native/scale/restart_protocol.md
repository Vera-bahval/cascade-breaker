# Same-database FinBot recovery

Freeze the post-authorization fixture plan before running. The eight obligations are TH720@E, H3@B, TH683@C, TH504@B, H1@E, TH689@C (one exact recorded transfer in the OFF natural cohort), TH510@B (canonical confirmation OFF) and TH601@C (the clear archived and native continuation). Use existing legitimate vendor profiles, invoice descriptions and principals. Seed an approved native invoice for each arm. This study begins after invoice and risk review. It conditions on an authorized normal-path payment and does not adjudicate authorization or induce a new one.

For each obligation, run OFF and receipt-bound recovery at three checkpoints: immediately before dispatching FinStripe (negative control), after the successful FinStripe return but before recording paid, and after the paid write but before communication. Use the stock agent loop, delegation, simulated tools and trace hook. Fixed outputs stand in for model choices in offline runs. End the first worker abruptly using process exit after saving the trace. Verify committed state independently in read-only SQLite between workers. Start a new worker with the very same database file, namespace and invoice IDs in each cell. Both workers have identical native vendor sessions and no external tools.

OFF retries the canonical payment steps from the payment delegation. The prescribed Payments sequence reads invoice and vendor, submits the unchanged transfer only while approved, and binds the latest receipt to local paid. In the already-paid OFF checkpoint it honors the stock prompt's refusal to issue another transfer for paid status. The prescribed parent uses status_update if this run reports no newly successful payment and sends confirmation if it did. This baseline describes one fixed stock-allowed retry sequence and does not estimate autonomous retry behavior. The receipt adapter uses a durable experiment journal of the native return to verify precise tax, reference, account, namespace, invoice and principal binding against the simulator's persisted transaction and registered invoice/vendor. It uses the original payment workflow if no transaction exists. For a verified committed payment it completes any missing native paid write, returns the already-completed outcome to the parent, and requests a payment confirmation for that single actual payment. It never infers settlement from text, invoice status alone, or a sibling obligation. Communication and task completion use the actual native tools.

Success requires one total completed transfer, original receipt preserved if one exists, the local paid note bound to that receipt, exactly one stored outbound vendor payment_confirmation with precise reference, principal and receipt, and parent success after delivery. Distinguish technical stops, duplicate money, incomplete or incorrect communication and no-commit control progress. Gross duplicate simulated principal is the sum of completed target transfers above the one intended payment.

A secondary Eliza test is planned for TH510@B and TH601@C with the post-FinStripe checkpoint, in paired OFF and receipt arms. The actual restart uses the same source, worker split, SQLite and native tools. Replay the single parent payment delegation to fix reach; all subsequent payment, communication and completion choices are autonomous. Compare realized effects, including non-reach or incomplete communication, with the offline prescribed retry. Cap all settled charges plus outstanding reserves at $0.10 on one recorded ledger, no Jev and no provider retry. Report this as a forced checkpoint experiment, not a power-loss, concurrent-retry, post-mail, or natural timeout study. The experiment journal is an added prerequisite. It captures a returned receipt and cannot recover a lost response between commit and receipt observation.
