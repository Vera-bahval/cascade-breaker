# Что дают низкие пороги Jev перед Fraud

По сохранённым ответам официального `jev-1.14.0` на 193 пакета посчитаны два правила. Первое сохраняет выбор API и требует, чтобы вероятность выбранного закрытия достигла порога. Второе закрывает Fraud с `CLOSE_ALLOW`, когда вероятность этого класса достигает порога, в том числе когда API выбрал `DEFER`. При `DEFER` расследование продолжает штатный Fraud. `CLOSE_ALLOW` завершает только проверку Fraud. Для `CLOSE_STOP` среди 193 пакетов нет подтверждённых примеров, API его ни разу не выбрал и его максимальная оценка ниже 0,10.

Во всех таблицах ниже использован эталон после дополнительной проверки источников. `INSUFFICIENT` означает, что проверяющие не установили правильное действие. Для него отдельно считаются потенциальные закрытия. Первоначальные метки сохранены в JSON для проверки чувствительности.

Среди шести исходных закрытий одно ошибочно в разработке с оценкой 0,51. В отложенных данных есть три сохранённых равенства 0,50 против 0,50 между `CLOSE_ALLOW` и `DEFER`. API выбрал `CLOSE_ALLOW` один раз и `DEFER` дважды. Порог 0,50 непосредственно по оценке `CLOSE_ALLOW` включает оба случая, где API выбрал `DEFER`. Расчёт использует значения в квитанциях с их сохранённой точностью.

## Если закрывать по оценке CLOSE_ALLOW

В ячейках указаны верные, ошибочные и неопределённые закрытия. Остальные пакеты передаются Fraud. Четырнадцать отложенных E входят в 104 отложенных, а 104 входят в 193. При каждом пороге переоцениваются те же пакеты.

При 0,35 на отложенных E можно было бы закрыть 9 из 10 допустимых случаев, но на разработке тот же порог включает ошибочное закрытие и ещё одно с неопределённой меткой. В этой группе на разработке максимальная оценка ошибочного закрытия совпадает с общей максимальной оценкой 0,51. Поэтому ни один порог по `CLOSE_ALLOW` не даёт в разработке хотя бы одного подтверждённого закрытия без ошибок. Это ретроспективная проверка чувствительности. Пороги не выбирались по отложенным данным, новые вызовы не выполнялись, в живой ветке действует заранее зафиксированная передача Fraud.

## Что было в 26 первых запусках E с вызовом Jev

API вернул 25 `DEFER` и один `CLOSE_ALLOW`. В самом эксперименте все 26 переданы штатному Fraud. Оценка `CLOSE_ALLOW` лежала от 0,15 до 0,52. Для четырёх запусков сохранённая проекция запроса точно совпала с независимо размеченной проекцией того же семейства. У 19 семейство совпало при изменившемся входе, для трёх не нашлось эталонного пакета. Поэтому точность по всем 26 не установлена.

| Порог по CLOSE_ALLOW ≥ | Предложенных закрытий из 26 | Верные по совпавшему входу | С неопределённой меткой | Без метки на этом входе |
| ---: | ---: | ---: | ---: | ---: |
| 0,30 | 23 | 3 | 1 | 19 |
| 0,35 | 20 | 3 | 1 | 16 |
| 0,40 | 14 | 2 | 1 | 11 |
| 0,45 | 5 | 0 | 1 | 4 |
| 0,50–0,52 | 1 | 0 | 1 | 0 |
| 0,53 | 0 | 0 | 0 | 0 |

В четырёх точных совпадениях штатный Fraud запустился и завершил проверку, не вызвал постановку счёта на расследование, а далее по каждому счёту прошёл один перевод. Эталон поддерживает сокращение Fraud в трёх из этих случаев. Jev вернул по ним `DEFER`. В четвёртом, `clean_29`, Jev выбрал `CLOSE_ALLOW` с оценкой 0,52. Первоначальная метка поддерживала закрытие, а сверка источника оставила `INSUFFICIENT`, поскольку проверяющий потребовал независимо сверить цену и объём заказа. С назначением A совпадает исходное состояние `clean_29`: штатный Fraud также не выставил флаг, и перевод завершился. В E штатный агент получил управление на той же границе непосредственно после Jev и мог выполнять собственные запросы. Это сравнение наблюдаемых действий на совпавших входах; автономного запуска Jev для этого случая не проводили.
