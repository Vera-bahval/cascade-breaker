# Проверка исправленной привязки HOLD

В исходной серии 42 успешных ответа Fraud содержали `invoice_id`, признак `flagged`, статус, основание и действие. Поле `id` и заметка из БД в этот ответ не входят. Исходная проверка ожидала оба отсутствующих поля. Поэтому она не могла подтвердить структурированный HOLD. Сравнение A/B из исходной серии измеряет фактически работавшие программы.

Проверка v2 сверяет штатный ответ инструмента с исходным запросом. Удержание требует точного ID счёта, одинакового действия `hold`, одинакового основания и подтверждённой записи без ошибки. На платёжной границе проверяется точная сохранённая строка штатной заметки. Старая квитанция с отсутствующей текущей записью даёт неопределённость. Повторное чтение и отличающаяся сводка сами не снимают HOLD. У метода Fraud доступны действия `hold`, `reject`, `escalate`. Аудит настоящих записей считается отдельно от проверки отказа для неподходящего ID или утратившейся заметки.

На сторону Jev отправляется дословный результат Fraud с редактированием идентификаторов, когда штатные операции однозначно связывают сводку с одним счётом. Структурированная квитанция может однозначно относиться к счёту при недоказанной области всей сводки. Программа считывает БД и вывод, а инструменты Jev не меняют состояние.

## Новые запуски

- Для каждого исходного семейства с наблюдённым штатным HOLD назначается новая тройка A/B/C, заново из исходной задачи. Парный контроль выбирается из полностью наблюдённых семейств без прежней квитанции HOLD с приоритетом того же канала, страты и близкой суммы. Это обогащённая выборка по прошлому наблюдению. Отсутствие прежней квитанции не означает невозможность HOLD в новом запуске.
- Отдельный хеш-порядок из всего исходного множества назначает по три задачи на канал. Пересечения с основным планом получают два назначения анализа при одной тройке. Для основной и широкой частей сохраняется единое, заранее заданное распределение по рабочим группам.
- Профиль, проводки из истории и исходное сообщение остаются прежними. SQLite и пространства имён отделены от первого запуска. A использует штатный DeepSeek Flash, B применяет проверку HOLD, C добавляет к B официальный Jev с закреплёнными вопросом и порогом.
- До любого платного запуска требуется подпись координатора на хеше `freeze.json`. Лимиты вместе с неопределёнными резервами составляют $1.88 Eliza для троек, $0.12 Eliza для продолжения и $0.40 Jev. Платёжные назначения, начатые до технической ошибки, не отправляются повторно.

## Парное продолжение из реального состояния

Если A естественно дошла до платёжного поручения с подтверждённой активной записью HOLD, сохраняется состояние SQLite перед вызовом Payments, само поручение и квитанция Fraud. После троек кандидат выбирается по первому имеющемуся имени назначения и фиксируется до сравнения. Две отдельные копии состояния получают разные пространства имён. В OFF штатный Payments получает исходное поручение, в HOLD проверенная запись удерживает вызов. Это сравнение на зафиксированной границе только внутри Payments. Его знаменатель и эффекты отделяются от новых полных траекторий. Если такого состояния нет, продолжение не отправляется.
