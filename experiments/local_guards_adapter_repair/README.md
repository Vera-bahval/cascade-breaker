# Исправление адаптеров FinBot

Подготовка повторного анализа сохранённых исполнений. В этом каталоге находятся
входы и проверки преобразований. Сравнительный эксперимент здесь ещё не проведён.
Основной отчёт исследования этим изменением не редактируется.

## Что исправлено

Ранее факты v4/v4.2 заполнялись только в условном replay. Теперь найденные
значения сохраняются в общем журнале и передаются всем совместимым
представлениям. Отсутствие факта, устаревание, невозможность выразить его в
формате метода и требования самого метода отражаются раздельно.

Входы исходных правил сохраняют собственную семантику. v1/v2 используют
начальное состояние и исходный конструктор. v3 сохраняет начальную или первую
наблюдавшуюся сумму и получателя. Платёжные доказательства v4 используют
актуальное наблюдение. Исходные native/native_core сохраняют прежнее отношение
к повторной оценке Fraud. Название агента не подтверждает техническую роль v4.
Роль восстанавливается по проверенному runner, классу и цепочке вызовов.
В P2 сохраняется также роль фактического дочернего исполнителя. Свойства
конструктора сессии передаются как свойства тестового запуска; это не
подтверждение веб-аутентификации или разрешения на доступ к объекту.

Текущий вызов ранней проверки сохраняется отдельно от предшествующей истории.
Аудит сверяет его инструмент, объект, сумму и целевой статус с исходным событием.
Идентификатор подтверждённого перевода связывается с payment_reference только
при совпадении счёта, вендора и самой ссылки. Неуспешная попытка такого
подтверждения не создаёт.

v4.3 отдельно меняет приём доказательств. Успешный связанный native HOLD
сохраняется независимо от неизвестной сессии, названия агента и непрозрачных
изменений БД. Изменяемые значения требуют непрерывной истории до действия.
HOLD снимается только последующим независимым подтверждением. Пороговые суммы,
права инструментов, применимость по этапам и профили A/B взяты из v4.2.
Неизвестное обязательное разрешение по-прежнему исключает ALLOW.
Последняя версия native-записи отслеживается отдельно от изменяемых полей:
ответ с новой версией и одними заметками не оставляет старую версию текущей.
Запись без новой версии снимает подтверждение прежней актуальности.

## Состав входов

Состав закреплён inventory.json на основании ревизии 5f947a38. Это 542 состояния
P4, 128 ранее размеченных ранних действий и 18 676 точек в 754 эпизодах.
Старые метки, модели и результаты проверяются по frozen-sources.json.

- common содержит сведения исходного запроса DeepSeek. Сопоставление включает
  system prompt, параметры, порядок событий и предлагаемое действие.
- expanded дополняет тот же префикс доказанными сведениями архивного запуска.
  Итоговые базы для восстановления входа не используются.
- conditional регистрирует локальный технический контекст на основании
  подтверждённого пути запуска. Положительные технические доказательства
  помечены replay. Они относятся к этой локальной среде.
- Для ранней серии historical использует исходные события и подтверждённые
  начальные условия. conditional добавляет указанное техническое сопровождение.

Внутренний интерфейс состоит из build_evidence(row, source), adapt(bundle,
method) и payload с сопровождающей coverage. records сохраняет наблюдения,
current содержит последнее значение с оценкой актуальности, baseline хранит
основание прежних сравнений. Производитель допускает источники по хешам.
Доверенные источники и ограничения полей перечислены в field-map.json.
JSON с полем source сам по себе не аутентифицирует произвольного отправителя.

Состояние и право на действие проверяются отдельно. Например, native статус
approved не создаёт человеческого одобрения. Служебный ID вызова, вычисленный
из координат журнала, обозначает конкретное наблюдение. Он не является
исторической записью аутентификации или независимым разрешением.

## ML и сохранённые ответы

methods.json фиксирует реализации, модели, преобразователи, пороги, дополнительные
проверки, размещения и варианты. Сохранены архивные ML, обе версии переобученных
ML и прежние v3-модели с их зафиксированными порогами и сочетаниями с правилами.
Для текстовой диагностики v3 используется прежний способ получения invoice/agent
text из начальных условий, чтений и парных возвратов делегирования.

В пакетах сохранены признаки, их хеши и хеши входов. Полный контракт вывода
связывается с записью methods.json. Смысл категорий evidence_status сохранён;
значения обновляются по исправленному доказательству. Дополнительные поля
coverage не становятся признаками ML. Новое значение входа требует нового
локального вывода модели после допуска к эксперименту. Обучение, пересчёт порогов и подмена
определений признаков в эту работу не входят.

Сохранённый DeepSeek сопоставляется с common по query_id. В expanded и
conditional поле query_id отсутствует. Для прямого сравнения с ними нового
ответа DeepSeek здесь нет. Подготовка не открывает файл ответов.

## Воспроизведение подготовки

Команды выполняются из корня рабочего дерева. Используйте существующее Python
окружение с numpy, scikit-learn и catboost. environment.json фиксирует версии.

```sh
python -m unittest experiments.local_guards_adapter_repair.test_evidence experiments.local_guards_adapter_repair.test_prepare -v
python -m experiments.local_guards_adapter_repair.registry
python -m experiments.local_guards_adapter_repair.prepare --output /tmp/finbot-repaired-inputs
python -m experiments.local_guards_adapter_repair.audit --inputs /tmp/finbot-repaired-inputs
```

inventory.py выполняет выделение идентификаторов и хеширование старых артефактов.
Для воспроизведения закреплённого состава используйте опубликованные inventory.json
и frozen-sources.json. Нужны прежние архивы и исходная БД, перечисленные в
local_guards_final_replay/EXPANDED.md. Два компонента старого архивного reader
пока используют расположение источников в исходном workspace. Хеши содержимого
проверяются до использования. Перенос источников требует настройки расположения,
с сохранением их байтов и манифестов.

Подготовка запрещает чтение меток, вердиктов защитников и файлов итоговых БД,
а также сетевые соединения. Она не вызывает правила, классификаторы или их
итоговые проверки допуска. Тесты отдельных контролей вызывают правила и
сценарный исполнитель, чтобы проверить корректность и STOP.

## Допуск и следующий этап

manifest.json фиксирует состав, исходный код и все подготовленные shards.
Независимое ревью связывается с точным коммитом и хешем этого манифеста.
approval.json появляется только после устранения существенных замечаний.
Любое изменение входов или кода аннулирует допуск.

Команда следующего этапа, требующая независимого допуска, например для v4.3
на общем платёжном входе, приведена ниже. Она подготовлена, но в этой работе
не запускается.

```sh
python -m experiments.local_guards_adapter_repair.execute_reviewed \
  --inputs experiments/local_guards_adapter_repair/inputs \
  --approval experiments/local_guards_adapter_repair/approval.json \
  --dataset p4 --mode common --method v4.3 --profile A \
  --output /tmp/finbot-v43-common-predictions.jsonl.gz
```

Для других методов выбирается точное имя из methods.json. Архивные ML используют
raw/calibrated/gated, переобученные ML raw/gated, v3 ML frozen. Каждый запуск
выполняется отдельным процессом, чтобы сохранить исходные имена модулей в pickle.
Проверка запуска не читает разметку и не создаёт итоговые таблицы качества.
Оценка качества, парные сравнения и обновление отчёта относятся к следующему этапу.

Известные примеры и разметка уже раскрывались при предыдущей работе. Будущий
анализ является исправленным повторным анализом открытых архивных данных.
