## 1. Что изменено (`finbot-cp3/scripts/runner_cp3_full.py`; копия до правки — `patches/runner_cp3_full.v4-before-receipt-diag.py`)

1. **Технический исход `completed_transfer_receipt_not_applied`** (поле `technical_outcome`). Ставится, только если
   прогон технический и одновременно:
   - ровно одна транзакция, `completed`, `receipt_applied = 0`;
   - квитанция FinStripe = SQLite, получатель = справочник;
   - у каждого вызова `create_transfer` есть результат;
   - счёт остался `approved`.
   Такой прогон — технический, побочный эффект считается определённым, серия идёт (с прочими лимитами). Если не
   выполнено хоть одно условие — по-прежнему `critical:side_effects_unclear`.
2. **Диагностика ответов не `completed`** (событие `response_diag`, без текста): `generation_id`, наличие `output`, число
   элементов, наличие `usage`, `error.code`; время запроса и ответа (`ts`).
3. **Сверка стоимости** для `failed`/`incomplete` без стоимости: бесплатный `GET /api/v1/generation?id=…`, результат пишется
   в `cost_lookup` (`total_cost`, токены, провайдер, `cancelled`, HTTP-статус). **Резерв не снимается автоматически** —
   только через `reconciliation.json` по отдельному согласованию.
4. **Возобновление после TH654-B.** Строка, остановившая серию, переоценивается по текущим правилам только для чтения
   (`rows.jsonl` не меняется): TH654-B → `completed_transfer_receipt_not_applied`, решение теперь «продолжать».
   Возобновление разрешено с причиной `reclassified:completed_transfer_receipt_not_applied`. Остальные критические причины
   по-прежнему не возобновляются.
5. Скрипт анализа: описательный счётчик `completed_transfer_receipt_not_applied` по веткам (на сегменте 1: B — 1,
   TH654-B). Основной и FIN-POLICY-1-анализ не менялись.
